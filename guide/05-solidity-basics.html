本章目标 ​

完成这一章后，你应该能够：

  • 写出带状态变量、映射、修饰器与自定义错误的合约。
  • 区分 storage、memory、calldata，知道什么时候必须写哪一个。
  • 实现一个最小 ERC-20 风格的代币，并解释 transfer 与 transferFrom 的授权关系。
  • 用 Hardhat 为合约写单元测试，覆盖成功路径与 revert 路径。

前置检查 ​

  • 已完成 第 04 章 · 以太坊与 EVM。
  • 知道账户、存储与 Gas 的基本关系。
  • 本机已安装仓库依赖（pnpm install）。

本章示例位于 examples/05-solidity-basics，合约是 MiniToken.sol。它不是可以直接上主网的生产代币，而是把 ERC-20 的关键结构抽出来，方便逐行阅读。

1. 一个合约由什么组成 ​

Solidity 合约通常包含五类东西：

组成部分作用本章示例
状态变量永久写入存储name、balanceOf、totalSupply
函数读写状态或只读计算transfer、approve、mint
事件给链下留下日志Transfer、Approval
错误失败时返回结构化原因InsufficientBalance
修饰器在函数执行前后加检查onlyOwner

先看状态变量与映射：

solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

/// @title MiniToken
/// @notice 教学用的最小 ERC-20 风格代币：没有外部依赖，便于逐行阅读。
contract MiniToken {
    // #region token-state
    string public name;
    string public symbol;
    uint8 public constant decimals = 18;
    uint256 public totalSupply;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    address public owner;
    // #endregion

    // #region errors-events
    event Transfer(address indexed from, address indexed to, uint256 value);
    event Approval(address indexed owner, address indexed spender, uint256 value);

    error ZeroAddress();
    error InsufficientBalance(address account, uint256 balance, uint256 needed);
    error InsufficientAllowance(address spender, uint256 allowed, uint256 needed);
    error NotOwner(address caller);
    // #endregion

    modifier onlyOwner() {
        if (msg.sender != owner) revert NotOwner(msg.sender);
        _;
    }

    constructor(string memory name_, string memory symbol_, uint256 initialSupply) {
        name = name_;
        symbol = symbol_;
        owner = msg.sender;
        _mint(msg.sender, initialSupply);
    }

    // #region transfer
    function transfer(address to, uint256 amount) external returns (bool) {
        if (to == address(0)) revert ZeroAddress();
        _transfer(msg.sender, to, amount);
        return true;
    }

    function _transfer(address from, address to, uint256 amount) internal {
        uint256 balance = balanceOf[from];
        if (balance < amount) revert InsufficientBalance(from, balance, amount);

        balanceOf[from] = balance - amount;
        balanceOf[to] += amount;

        emit Transfer(from, to, amount);
    }
    // #endregion

    // #region approve
    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        emit Approval(msg.sender, spender, amount);
        return true;
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        if (to == address(0)) revert ZeroAddress();

        uint256 allowed = allowance[from][msg.sender];
        if (allowed < amount) revert InsufficientAllowance(msg.sender, allowed, amount);

        allowance[from][msg.sender] = allowed - amount;
        _transfer(from, to, amount);
        return true;
    }
    // #endregion

    // #region mint
    function mint(address to, uint256 amount) external onlyOwner {
        if (to == address(0)) revert ZeroAddress();
        _mint(to, amount);
    }

    function _mint(address to, uint256 amount) internal {
        totalSupply += amount;
        balanceOf[to] += amount;
        emit Transfer(address(0), to, amount);
    }
    // #endregion
}

几个细节：

  • public 状态变量会自动生成同名 view 函数，例如 balanceOf(alice)。
  • mapping(address => uint256) 不能遍历，也不能返回整个映射；只能按 key 查询。
  • constant 在编译期确定，不占存储槽，读取不消耗存储 Gas。
  • allowance[owner][spender] 是嵌套映射，表示“owner 允许 spender 花多少”。

public 不等于安全

public、private 都只是 Solidity 的可见性，不改变链上数据的公开性。任何写入存储的值都可以被节点读取。

2. 函数可见性与状态可变性 ​

两种修饰经常一起出现：

  • 可见性：public、external、internal、private。
  • 状态可变性：view（只读）、pure（不读状态）、默认（可写）。
solidity
function totalSupply() public view returns (uint256) // 只读
function transfer(address to, uint256 amount) external returns (bool) // 写状态
function _transfer(...) internal // 仅合约内部与子类可调用
1
2
3

经验规则：

  • 对外暴露的入口用 external，省一点 calldata 拷贝开销。
  • 内部复用的逻辑拆成 internal 函数，例如 _transfer、_mint。
  • 只要函数不写状态就标 view，方便链下 eth_call 直接读。

3. storage、memory 与 calldata ​

这三个关键字决定数据放在哪：

关键字位置生命周期典型场景
storage合约存储永久状态变量、storage 指针
memory内存单次调用函数内临时数组、字符串参数
calldata调用数据单次调用，只读external 函数的数组/字符串参数
solidity
function setName(string calldata newName) external {
    name = newName;            // calldata → storage，发生拷贝
}

function sum(uint256[] memory values) internal pure returns (uint256) { ... }
1
2
3
4
5

常见错误是给 external 函数的字符串参数写 memory：能编译，但会多一次不必要的拷贝。反过来，internal 函数不能使用 calldata 修饰普通参数。

这段代码体现了三个习惯：

  1. 先检查后修改：余额不足时立刻 revert，不留下中间状态。
  2. 内部函数复用：transfer 只负责入口校验，真正的记账在 _transfer。
  3. 事件跟随状态变化：每次余额变动都发 Transfer，链下索引才能重建历史。

balanceOf[from] = balance - amount 使用先读出的 balance，避免重复读取存储；balanceOf[to] += amount 则由编译器生成读改写。两者在 0.8 以后都带溢出检查。

ERC-20 的授权是两步：

流程是：

  1. owner 调用 approve(spender, amount)，写入 allowance[owner][spender]。
  2. spender 调用 transferFrom(owner, to, amount)，先扣减额度，再执行转账。

注意 transferFrom 里的 msg.sender 是 spender，而 from 是真正扣款的账户。这两者容易混淆。

授权额度是风险点

无限授权（approve(spender, type(uint256).max)）意味着 spender 可以随时转走你的全部余额。前端应在使用后把额度改回 0，或使用 increaseAllowance / decreaseAllowance 这类更安全的接口。

7. 修饰器与权限 ​

onlyOwner 把权限检查从业务逻辑里抽出来：

solidity
modifier onlyOwner() {
    if (msg.sender != owner) revert NotOwner(msg.sender);
    _;
}
1
2
3
4

_ 是占位符，表示被修饰函数的主体。修饰器适合做“进入前检查”，但不要把复杂的业务逻辑塞进去，否则调用顺序会变得难以推理。

9. 常见坑 ​

  • 把 memory 当成“更安全”：它只是位置不同，storage 指针写错会改到真实状态。
  • 在循环里写存储：每轮一次 SSTORE，Gas 会迅速失控。
  • 忘记零地址检查：transfer(address(0), ...) 会把代币永久锁死。
  • 在 transferFrom 里用 from 当 msg.sender：授权检查会完全失效。
  • 事件参数顺序与前端解析不一致：索引参数与非索引参数的顺序必须和 ABI 对齐。
  • 用 require 字符串代替自定义错误：长字符串会显著增加部署与执行成本。
