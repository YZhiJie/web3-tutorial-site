02 · 钱包、地址、助记词与签名 ​

零基础约 5 学时 前置：/guide/01-blockchain-crypto验证于 2026-11-04

本章目标 ​

完成这一章后，你应该能够：

  • 说清助记词、种子、派生路径、私钥、地址的关系。
  • 用 BIP-39/BIP-32/BIP-44 从一个助记词派生多个账户。
  • 区分交易签名与消息签名，理解 EIP-191 与 EIP-712 的用途。
  • 识别常见钱包风险：助记词泄露、恶意签名、地址投毒。

前置检查 ​

  • 已完成 第 01 章 · 区块链与密码学基础。
  • 知道私钥、公钥与地址的派生关系。
  • 准备好一个只放测试资产的浏览器钱包。

1. 钱包管理的是密钥，不是币 ​

“钱包里有 1 ETH”只是界面上的说法。链上真正记录的是地址余额，钱包本地保存的是能控制该地址的私钥或助记词。

因此：

  • 卸载钱包 ≠ 资产消失；只要助记词还在，就能恢复。
  • 备份钱包 = 备份助记词；截图、云笔记、聊天记录都不安全。
  • 导入别人的助记词 = 把资产控制权交给对方。

2. 助记词与派生路径 ​

BIP-39 把随机熵编码成 12/24 个可抄写的单词；BIP-32 定义层级确定性钱包（HD Wallet）；BIP-44 规定以太坊的派生路径：

text
m / 44' / 60' / 0' / 0 / index
    │     │     │    │    └─ 账户序号
    │     │     │    └─ 外部链（收款地址）
    │     │     └─ 账户索引
    │     └─ 币种 60 = ETH
    └─ BIP-44

同一个助记词，只要派生路径不同，就会得到不同地址。这也是为什么“同一个助记词在两个钱包里地址不一样”很常见。

js
// BIP-39 助记词 -> BIP-32 种子 -> BIP-44 派生路径 -> 私钥 -> 地址
export function deriveAccount(mnemonic, index = 0) {
  const path = `m/44'/60'/0'/0/${index}`
  const wallet = HDNodeWallet.fromPhrase(mnemonic, undefined, path)
  return {
    path,
    address: wallet.address,
    privateKey: wallet.privateKey
  }
}

测试助记词也只能用于测试

示例使用的是 Hardhat 公开测试助记词，全网都知道它的私钥。真实钱包必须使用自己生成、且从未联网泄露的助记词。

3. 地址与校验和 ​

地址是 20 字节，通常写成 0x 开头的 40 位十六进制。EIP-55 用大小写编码校验和：

  • 0x7E5F4552091A69125d5DfCb7b8C2659029395Bdf 是合法校验和格式。
  • 全小写地址在多数工具里仍可使用，但复制粘贴时更容易出错。
  • 转账前应核对完整地址，不要只看首尾几位。

地址投毒攻击正是利用“只看首尾”的习惯：攻击者生成一个首尾与你常用地址相似的新地址，诱导你从历史记录里复制错误地址。

4. 两种签名：文本签名与结构化签名 ​

EIP-191：给普通文本签名 ​

钱包会在消息前加上固定前缀，避免把“签名消息”伪装成“签名交易”。

js
// EIP-191：给普通文本签名，钱包会先加上前缀再哈希
export async function signText(privateKey, message) {
  const wallet = new Wallet(privateKey)
  const signature = await wallet.signMessage(message)
  return {
    signature,
    recovered: verifyMessage(message, signature)
  }
}

适用场景：登录证明、 ownership 验证。缺点：用户在钱包里看到的往往是一段难读的文本，容易盲目确认。

EIP-712：给结构化数据签名 ​

EIP-712 把字段、类型与 domain 一起纳入签名，钱包可以展示成可读表单：

js
// EIP-712：结构化数据签名，钱包会展示字段而不是一串不可读的哈希
export const loginDomain = {
  name: 'Web3 Tutorial',
  version: '1',
  chainId: 31337
}

export const loginTypes = {
  Login: [
    { name: 'user', type: 'string' },
    { name: 'nonce', type: 'uint256' }
  ]
}

export async function signLogin(privateKey, message) {
  const wallet = new Wallet(privateKey)
  const signature = await wallet.signTypedData(loginDomain, loginTypes, message)
  const recovered = verifyTypedData(
    loginDomain,
    loginTypes,
    message,
    signature
  )
  return { signature, recovered }
}

domain 中的 chainId 很关键：同一个签名换到另一条链就不应该继续有效。

签名不是“免责声明”

恶意网站可以构造一笔看起来像登录、实际授权转账的签名。签名前必须在钱包里核对：链、合约地址、方法、金额、接收方。

5. 钱包类型与安全边界 ​

类型私钥位置优点风险
浏览器插件钱包本地加密存储使用方便恶意网站诱导签名、插件漏洞
硬件钱包离线设备私钥不触网盲签、钓鱼网站伪造收款方
多签钱包链上合约分散单点风险签名者被社工、治理攻击
托管钱包交易所/第三方门槛低平台风险、提现限制

入门阶段的建议：

  1. 浏览器钱包只放测试资产。
  2. 助记词手写在离线纸张上，不拍照、不粘贴到任何网页。
  3. 任何要求“输入助记词以验证/升级/领取空投”的页面，一律视为诈骗。

6. 常见坑 ​

  • 把助记词当成密码：助记词没有“修改密码”一说，泄露即永久失控。
  • 在不同链上复用同一签名：没有 chainId 绑定的签名可能被跨链重放。
  • 只看地址首尾：地址投毒就是针对这个习惯。
  • 在网页里粘贴私钥：网页永远不该接触你的私钥或助记词。
  • 以为硬件钱包绝对安全：设备只保证私钥不出网，签名内容仍需要你核对。

7. 练习题 ​

  1. 用 deriveAccount 派生 index 0–4 的地址，观察路径与地址的对应关系。
  2. 修改 EIP-712 示例中的 chainId，确认验签结果变化。
  3. 写一个函数：给定消息与签名，返回恢复出的地址，并拒绝被篡改的消息。
  4. 找一个真实钱包的“签名请求”截图，逐项标出链、合约、方法与金额。
