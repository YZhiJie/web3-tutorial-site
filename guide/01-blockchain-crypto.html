01 · 区块链与密码学基础 ​

1. 区块链到底解决了什么问题 ​

传统数据库里，谁有写权限谁就能改数据。区块链把“记账权”分散给许多节点，并让每个节点都能独立验证历史：

它的核心不是“把数据放到链上”，而是让不信任彼此的参与方，用密码学与共识规则共同维护一份可验证的历史。本章先讲最底层的密码学零件。

2. 哈希：把任意数据变成固定长度的指纹 ​

哈希函数把任意长度的输入映射为固定长度的输出。区块链里最常用的是 Keccak-256（注意不是 SHA-256，两者输出长度相同但算法不同）。

三个关键性质：

性质含义在链上的用途
确定性同一输入永远得到同一输出任何人都能复算区块哈希
抗碰撞很难找到两个不同输入得到同一输出区块指纹、地址、交易 ID
单向性从输出无法反推输入防篡改、承诺、密码派生

下面这段代码来自本章示例工程：

js
// 同一输入永远得到同一结果；输入变一个字符，输出完全不同
export function keccak(text) {
  return keccak256(toUtf8Bytes(text))
}

export function sha256Text(text) {
  return sha256(toUtf8Bytes(text))
}

// 哈希不能反推出原文，只能通过“重新计算 + 比对”来验证
export function verifyHash(text, expectedHash) {
  return keccak(text) === expectedHash
}

哈希不是加密

哈希是单向的，没有“解密”。所谓“验证哈希”，本质是拿原文重新算一遍，再和已知结果比对。

几个必须记住的结论：

  • 私钥不能泄露：拿到私钥就等于拿到账户的全部控制权，链上交易无法撤回。
  • 地址不是私钥：地址可以公开收款，但它无法用来签名。
  • 地址有校验和：EIP-55 用大小写混合编码校验和，输错一个字符通常无法通过校验。

不要用示例私钥

示例中的私钥来自公开测试数据。任何出现在教程、截图、代码仓库里的私钥都必须视为已泄露。

4. 数字签名：证明“是我签的”，而不是“我本人” ​

签名过程大致是：

  1. 对消息计算摘要（哈希）。
  2. 用私钥对摘要做椭圆曲线签名。
  3. 任何人用签名、消息和签名者地址，就能在本地验证。
js
export async function signAndVerify(privateKey, message) {
  const wallet = new Wallet(privateKey)
  const signature = await wallet.signMessage(message)
  const recovered = verifyMessage(message, signature)
  return { signature, recovered, matches: recovered === wallet.address }
}

5. Merkle 树：用一条路径验证一批数据 ​

一个区块可能包含几百笔交易。如果验证者要下载全部交易才能确认某一笔存在，成本会很高。Merkle 树把交易两两哈希，层层向上，最终得到一个根哈希：

验证某笔交易时，只需要它的兄弟节点路径（Merkle Proof），复杂度从 降到 ：

js
function hashLeaf(value) {
  return keccak256(toUtf8Bytes(value))
}

function hashPair(left, right) {
  // 左、右位置固定：顺序本身就是 Merkle 证明的一部分
  return keccak256(concat([left, right]))
}

export function buildMerkleLayers(values) {
  if (values.length === 0) throw new Error('至少需要一个叶子节点')

  const layers = [values.map(hashLeaf)]
  while (layers.at(-1).length > 1) {
    const current = layers.at(-1)
    const next = []
    for (let i = 0; i < current.length; i += 2) {
      const left = current[i]
      const right = current[i + 1] ?? left
      next.push(hashPair(left, right))
    }
    layers.push(next)
  }
  return layers
}

export function merkleRoot(values) {
  return buildMerkleLayers(values).at(-1)[0]
}

export function merkleProof(values, index) {
  if (index < 0 || index >= values.length) throw new Error('索引越界')

  const layers = buildMerkleLayers(values)
  const proof = []
  let cursor = index

  for (let level = 0; level < layers.length - 1; level++) {
    const layer = layers[level]
    const siblingIndex = cursor % 2 === 0 ? cursor + 1 : cursor - 1
    const sibling = layer[siblingIndex] ?? layer[cursor]
    proof.push(sibling)
    cursor = Math.floor(cursor / 2)
  }
  return proof
}

export function verifyMerkleProof(value, proof, root, index) {
  let current = hashLeaf(value)
  let cursor = index

  for (const sibling of proof) {
    // 根据当前节点在父节点中的左右位置决定拼接顺序
    current =
      cursor % 2 === 0 ? hashPair(current, sibling) : hashPair(sibling, current)
    cursor = Math.floor(cursor / 2)
  }
  return current === root
}

为什么叶子要单独哈希？

如果直接对两个叶子拼接后哈希，攻击者可能构造出“内部节点长得像叶子”的数据。先对叶子做一次哈希，可以区分叶子层与内部层，降低第二原像攻击风险。

6. 共识与账户模型 ​

维度PoWPoS
出块权算力竞争质押与验证者轮次
主要成本电力与硬件质押资金与罚没风险
最终性概率性，越久越难回滚有明确最终性检查点

账户模型方面，比特币使用 UTXO（未花费输出），以太坊使用 账户模型：

  • UTXO：每一笔花费都要引用之前的输出，像“找零”。
  • 账户模型：每个地址有一个余额与 nonce，交易直接修改余额，更接近银行账户。

以太坊的账户模型让智能合约的状态管理更自然，但也引入了 nonce 顺序、状态膨胀等问题，这些会在后续章节遇到。

7. 常见坑 ​

  • 把 Keccak-256 当成 SHA-256：两者输出都是 64 位十六进制，但结果完全不同。
  • 以为地址可以逆向出私钥：地址是单向派生结果，无法反推。
  • 把“签名”当成“加密”：签名用于证明来源与完整性，不用于保密传输。
  • 用同一个签名重复提交：没有 nonce/过期校验的签名可以被重放。
  • 以为 Merkle 根能证明“全部数据正确”：它只能证明某个叶子属于这棵树；根本身仍需要可信来源。
