09 · 部署与验证 ​

需入门约 5 学时 前置：/advanced/08-testing-local-chain验证于 2026-11-04

本章目标 ​

完成这一章后，你应该能够：

  • 写出可重复执行的部署脚本，而不是手动复制地址。
  • 解释 CREATE 与 CREATE2 的地址差异，并用公式预测合约地址。
  • 用 salt 与 init code 保证部署幂等，避免重复创建。
  • 在 Etherscan 上完成源码验证，并管理多条链的地址簿。
  • 知道哪些信息可以提交、哪些必须留在 .env。

前置检查 ​

  • 已完成 08 · 测试与本地链。
  • 能启动 hardhat node 并运行部署脚本。
  • 有一个可用的 Sepolia RPC（可选，本章测试不依赖它）。

本章示例位于 examples/09-deploy-verify，共 2 个合约、7 条测试。

1. 部署到底发生了什么 ​

部署合约就是一笔交易，交易数据是合约的 init code：

text
from:    部署者 EOA
to:      null（或工厂合约）
data:    init code
result:  receipt.contractAddress / 工厂事件里的新地址
1
2
3
4

两类地址来源：

方式地址决定因素是否可预测
CREATE部署者地址 + nonce可以，但 nonce 会变
CREATE2工厂地址 + salt + init code hash完全确定

CREATE2 的公式：

text
address = keccak256(0xff ++ factory ++ salt ++ keccak256(initCode))[12:]
1

2. 在部署前算出地址 ​

solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import './SimpleToken.sol';

/// @notice 用 CREATE2 部署 SimpleToken，地址可以在部署前算出来。
contract DeterministicFactory {
    // #region factory-predict
    event Deployed(address indexed token, bytes32 indexed salt, address indexed deployer);

    error AlreadyDeployed(address token);
    error DeployFailed();

    function initCodeHash(string memory name, string memory symbol, uint256 supply, address holder)
        public
        pure
        returns (bytes32)
    {
        return keccak256(
            abi.encodePacked(
                type(SimpleToken).creationCode,
                abi.encode(name, symbol, supply, holder)
            )
        );
    }

    function predictAddress(
        bytes32 salt,
        string memory name,
        string memory symbol,
        uint256 supply,
        address holder
    ) public view returns (address) {
        bytes32 hash = initCodeHash(name, symbol, supply, holder);
        return
            address(
                uint160(
                    uint256(keccak256(abi.encodePacked(bytes1(0xff), address(this), salt, hash)))
                )
            );
    }
    // #endregion

    // #region factory-deploy
    function deploy(
        bytes32 salt,
        string memory name,
        string memory symbol,
        uint256 supply,
        address holder
    ) external returns (address token) {
        address predicted = predictAddress(salt, name, symbol, supply, holder);
        if (predicted.code.length > 0) revert AlreadyDeployed(predicted);

        bytes memory initCode = abi.encodePacked(
            type(SimpleToken).creationCode,
            abi.encode(name, symbol, supply, holder)
        );

        assembly {
            token := create2(0, add(initCode, 0x20), mload(initCode), salt)
        }
        if (token == address(0)) revert DeployFailed();

        emit Deployed(token, salt, msg.sender);
    }
    // #endregion
}

两个函数分工明确：

  • initCodeHash 把构造参数编码进 init code，再取哈希。
  • predictAddress 按 CREATE2 公式拼出地址。

构造参数也是 init code 的一部分

改名字、改符号、改初始持有人，都会改变 init code hash，从而改变地址。前端显示“即将部署到 0x…”时，必须把完整参数算进去。

三个细节：

  1. predicted.code.length > 0 表示地址已有代码，直接以 AlreadyDeployed 拒绝。
  2. 用内联汇编调用 create2，返回值是零地址时说明部署失败。
  3. 事件带上 salt 与部署者，链下索引可以重建部署历史。

幂等的好处：脚本可以安全重跑，CI 重试不会产生第二个合约。

4. 部署脚本：输出机器可读的地址 ​

typescript
import { ethers, network } from 'hardhat'

// #region deploy-script
async function main() {
  const [deployer] = await ethers.getSigners()
  const salt = ethers.id(process.env.DEPLOY_SALT ?? 'web3-tutorial-v1')
  const name = 'Tutorial Token'
  const symbol = 'TUT'
  const supply = ethers.parseEther('1000')

  const factory = await ethers.deployContract('DeterministicFactory')
  await factory.waitForDeployment()
  const factoryAddress = await factory.getAddress()

  const predicted = await factory.predictAddress(salt, name, symbol, supply, deployer.address)
  const receipt = await (await factory.deploy(salt, name, symbol, supply, deployer.address)).wait()

  const code = await ethers.provider.getCode(predicted)
  if (code === '0x') throw new Error(`部署后地址没有代码：${predicted}`)

  const token = await ethers.getContractAt('SimpleToken', predicted)

  console.log(
    JSON.stringify(
      {
        network: network.name,
        chainId: Number((await ethers.provider.getNetwork()).chainId),
        deployer: deployer.address,
        factory: factoryAddress,
        token: predicted,
        name: await token.name(),
        symbol: await token.symbol(),
        totalSupply: (await token.totalSupply()).toString(),
        salt: ethers.hexlify(salt),
        block: receipt?.blockNumber ?? null
      },
      null,
      2
    )
  )
}
// #endregion

main().catch((error) => {
  console.error(error)
  process.exitCode = 1
})

脚本遵循四条规则：

  • 不把地址写死在源码里，每次从链上读。
  • 部署后立刻 getCode，零代码直接抛错。
  • 输出 JSON，方便写入地址簿或传给前端。
  • 私钥只从环境变量读取，缺失时明确失败。

Hardhat 的 dotenv/config 让 .env 在配置加载时可用；.env.example 只放占位符。

5. 源码验证 ​

验证的本质是：把源码、编译器版本、优化设置、构造参数提交给浏览器，让它重新编译并比对字节码。

bash
pnpm --filter @web3-ex/09-deploy-verify exec hardhat verify --network sepolia <ADDRESS>
1

带构造参数的合约需要显式传入：

bash
pnpm --filter @web3-ex/09-deploy-verify exec hardhat verify --network sepolia <ADDRESS> \
  "Tutorial Token" "TUT" 1000000000000000000000 0xYourAddress
1
2

常见失败原因：

  • 优化开关或 runs 与部署时不一致。
  • 构造参数类型/顺序不对（尤其是 uint256 与地址）。
  • 部署与验证用的不是同一份源码（本地改过但没重新部署）。

6. 多链地址管理 ​

推荐把部署结果放成“按链 ID 分组”的 JSON：

json
{
  "31337": { "factory": "0x...", "token": "0x..." },
  "11155111": { "factory": "0x...", "token": "0x..." }
}
1
2
3
4

原则：

  • 地址文件可以提交，私钥文件绝不提交。
  • 每条链单独记录部署块高，方便索引器从正确位置扫描。
  • 前端按 chainId 读取，不要假设所有链地址相同。

7. 测试覆盖 ​

bash
pnpm --filter @web3-ex/09-deploy-verify test
1

7 条测试验证：

  • 预测地址与实际部署地址一致。
  • 代币参数与初始持有人正确。
  • 同 salt 重复部署被拒绝。
  • salt、构造参数、工厂地址任一变化都会改变预测地址。
  • initCodeHash 稳定且对参数敏感。

8. 常见坑 ​

  • 把 msg.sender 当成部署者：在工厂里 CREATE2 部署时，构造函数看到的是工厂地址。
  • 用 EOA 的 nonce 预测地址：只要中间发过一笔交易，nonce 就变了。
  • salt 复用但参数不同：地址也会不同，别把 salt 当成唯一键。
  • 验证时漏传构造参数：字节码能对上，但构造参数校验会失败。
  • 把私钥写进 hardhat.config.ts：配置会进 Git 历史，等于泄露。
  • 部署脚本不检查代码：RPC 返回成功但地址没代码时，后续交互会静默失败。

9. 练习题 ​

  1. 给工厂增加 deployAndTransfer(salt, ..., holder, amount)，部署后把部分代币转给买家。
  2. 写一个脚本，读取地址簿 JSON 并检查每条链上的代码是否存在。
  3. 解释为什么 CREATE2 地址与交易发送者的 nonce 无关。
  4. 用同一个 salt 在两条不同链上部署，记录地址是否相同，并说明原因。
