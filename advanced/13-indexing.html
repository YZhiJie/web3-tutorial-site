13 · 链上数据与索引 ​

需入门约 6 学时 前置：/advanced/09-deploy-verify验证于 2026-11-04

本章目标 ​

完成这一章后，你应该能够：

  • 说清“读状态”和“读事件”的差异，知道什么时候必须索引。
  • 用 eth_getLogs 按区块分页拉取事件，并正确处理去重与排序。
  • 识别 reorg，设计“回滚 + 重扫”的恢复流程。
  • 用确认数区分“已上链”和“已最终确定”。
  • 判断什么时候该自建索引器，什么时候用 The Graph 或第三方 API。

前置检查 ​

  • 已完成 09 · 部署与验证。
  • 知道事件、topics 与 ABI 编码的基本关系。
  • 本机 Node 版本满足 .nvmrc。

本章示例位于 examples/13-indexing，纯 Node ESM，9 条测试，不需要数据库或网络。

1. 为什么需要索引 ​

链上只保证“当前状态”，历史查询要靠事件：

需求直接 RPC索引后
查当前余额eth_call / balanceOf可选
查某地址全部转账历史需要逐块扫描一次查询
按时间/金额筛选不支持支持
聚合统计几乎不可行方便

索引器的本质：把链上日志“拉下来、解码、存起来”，并持续追新块。

一次请求至少包含：

  "topics": ["0xddf252ad..."]

返回的每条日志包含：

  • address：发出日志的合约。
  • topics：topic0 是事件签名哈希，之后是 indexed 参数。
  • data：非 indexed 参数。
  • blockNumber、transactionHash、logIndex。

ERC-20 Transfer 的 from、to 是 indexed，value 在 data 里：

javascript
// #region decode
export const TRANSFER_TOPIC =
  '0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef'

function topicToAddress(topic) {
  return '0x' + topic.slice(26).toLowerCase()
}

export function decodeTransferLog(log) {
  if (!log) return null
  if (!Array.isArray(log.topics) || log.topics.length < 3) return null
  if (log.topics[0].toLowerCase() !== TRANSFER_TOPIC) return null
  if (typeof log.data !== 'string' || log.data.length < 3) return null

  try {
    return {
      from: topicToAddress(log.topics[1]),
      to: topicToAddress(log.topics[2]),
      value: BigInt(log.data),
      blockNumber: Number(log.blockNumber),
      transactionHash: log.transactionHash,
      logIndex: Number(log.logIndex)
    }
  } catch {
    return null
  }
}
// #endregion

3. 分页：不要一次扫全链 ​

公共 RPC 通常限制区块范围。索引器必须按页请求：

javascript
// #region indexer
function logKey(log) {
  return `${log.transactionHash}:${log.logIndex}`
}

function normalize(logs) {
  const seen = new Map()
  for (const log of logs) {
    seen.set(logKey(log), log)
  }
  return [...seen.values()].sort((a, b) => {
    const blockDiff = Number(a.blockNumber) - Number(b.blockNumber)
    if (blockDiff !== 0) return blockDiff
    return Number(a.logIndex) - Number(b.logIndex)
  })
}

export class LogIndexer {
  constructor({ getLogs, fromBlock = 0, pageSize = 1000 }) {
    if (typeof getLogs !== 'function') throw new Error('getLogs is required')
    if (pageSize <= 0) throw new Error('pageSize must be positive')

    this.getLogs = getLogs
    this.fromBlock = fromBlock
    this.pageSize = pageSize
  }

  async scan(toBlock) {
    if (toBlock < this.fromBlock) {
      return { logs: [], ranges: [], nextFromBlock: this.fromBlock }
    }

    const logs = []
    const ranges = []

    for (let start = this.fromBlock; start <= toBlock; start += this.pageSize) {
      const end = Math.min(start + this.pageSize - 1, toBlock)
      const page = await this.getLogs({ fromBlock: start, toBlock: end })
      ranges.push([start, end])
      logs.push(...page)
    }

    this.fromBlock = toBlock + 1

    return { logs: normalize(logs), ranges, nextFromBlock: this.fromBlock }
  }
}

export function reconcile({ existing, reorgFromBlock, replacement = [] }) {
  const kept = existing.filter((log) => Number(log.blockNumber) < reorgFromBlock)
  return normalize([...kept, ...replacement])
}

export function confirmedLogs(logs, headBlock, confirmations) {
  const safeBlock = headBlock - confirmations
  return normalize(logs.filter((log) => Number(log.blockNumber) <= safeBlock))
}
// #endregion

三个设计点：

  • pageSize 可配置，按 RPC 限制调整。
  • 每页记录 [start, end]，出问题时能定位到具体区间。
  • 扫描成功后游标前进到 toBlock + 1，下次从新位置继续。

分页会带来重复：重试、边界重叠、节点返回不一致，都可能让同一条日志出现两次。必须按 (transactionHash, logIndex) 去重。

4. 排序：链上顺序不是返回顺序 ​

节点不保证返回顺序。索引器应统一按：

text
blockNumber 升序 → logIndex 升序
1

否则前端分页、聚合和“最新一笔”都会出错。

5. reorg：链会回滚 ​

当区块被重组时，之前索引的日志可能不再属于主链。正确处理：

ts
const result = reconcile({
  existing,
  reorgFromBlock: forkBlock,
  replacement: newLogs
})
1
2
3
4
5

规则：

  1. 丢弃 blockNumber >= forkBlock 的旧日志。
  2. 用新扫描结果替换。
  3. 重新去重与排序。
  4. 更新游标到新链头。

只追加不回滚，会留下“幽灵交易”。

6. 确认数与最终性 ​

不同链的最终性不同：

链类型建议
PoW / 早期 PoS等待多个确认（如 12）
主流 L2等待 L1 最终确定或排序器确认
本地测试链无需等待

7. 实测脚本：从 RPC 拉一段日志 ​

javascript
import { LogIndexer } from '../src/indexer.mjs'
import { decodeTransferLog, TRANSFER_TOPIC } from '../src/decode.mjs'

// #region scan-script
const url = process.env.RPC_URL
const address = process.env.CONTRACT_ADDRESS

if (!url || !address) {
  console.error('需要设置 RPC_URL 与 CONTRACT_ADDRESS')
  process.exit(1)
}

async function rpc(method, params) {
  const response = await fetch(url, {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ jsonrpc: '2.0', id: 1, method, params })
  })
  const body = await response.json()
  if (body.error) throw new Error(`${method}: ${body.error.message}`)
  return body.result
}

async function main() {
  const latest = Number(await rpc('eth_blockNumber', []))
  const fromBlock = Number(process.env.FROM_BLOCK ?? Math.max(0, latest - 10_000))
  const toBlock = Number(process.env.TO_BLOCK ?? latest)
  const pageSize = Number(process.env.PAGE_SIZE ?? 2_000)

  const indexer = new LogIndexer({
    fromBlock,
    pageSize,
    getLogs: ({ fromBlock, toBlock }) =>
      rpc('eth_getLogs', [
        {
          address,
          fromBlock: '0x' + fromBlock.toString(16),
          toBlock: '0x' + toBlock.toString(16),
          topics: [TRANSFER_TOPIC]
        }
      ])
  })

  const { logs, ranges } = await indexer.scan(toBlock)
  const transfers = logs.map(decodeTransferLog).filter(Boolean)

  console.log(
    JSON.stringify(
      {
        fromBlock,
        toBlock,
        ranges,
        totalLogs: logs.length,
        transfers: transfers.slice(0, 20)
      },
      null,
      2
    )
  )
}
// #endregion

main().catch((error) => {
  console.error(error)
  process.exitCode = 1
})

8. 自建索引器 vs The Graph ​

方案优点代价
自建（本示例）完全可控、可离线测试需要处理 reorg、存储、扩容
The Graph声明式 subgraph、托管查询需要部署与维护 subgraph，链支持有限
第三方 API上手最快依赖服务商、配额与数据口径

选择建议：

  • 只是展示少量事件：直接 RPC + 缓存。
  • 需要复杂查询与聚合：自建或 The Graph。
  • 需要多链统一口径：优先考虑成熟的索引服务，并保留自建兜底。

9. 数据一致性 ​

索引器要保证三件事：

  1. 幂等：同一日志处理多次结果相同。
  2. 可回滚：知道从哪个区块开始重扫。
  3. 可对账：定期用 eth_getBalance / balanceOf 校验索引结果。

推荐存储主键：

text
chainId + transactionHash + logIndex
1

它同时解决去重与跨链冲突。

9 条测试：

  • 分页区间与请求次数。
  • 去重、排序、游标推进。
  • reorg 回滚与替换合并。

11. 常见坑 ​

  • 一次请求扫几十万块：多数 RPC 会超时或直接拒绝。
  • 只按 txHash 去重：同一交易可能有多条日志，必须加 logIndex。
  • 忽略 reorg：测试网尤其频繁，主网也可能发生。
  • 把最新块当最终数据：前端应区分“待确认”和“已确认”。
  • topic 顺序写错：indexed 参数的顺序决定 topics 下标。
  • 不记录游标：进程重启后从头扫描，成本高且容易重复。

12. 练习题 ​

  1. 给 LogIndexer 增加失败重试与指数退避，写测试模拟前两次失败。
  2. 实现一个按地址过滤的 transferHistory(address)，只保留 from 或 to 命中该地址的日志。
  3. 设计 checkpoint 的存储格式，说明进程崩溃后如何恢复。
  4. 用同一份日志分别测试“未确认”和“已确认”两个视图，验证边界区块。
