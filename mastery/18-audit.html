18 · 审计与形式化 ​

需进阶约 6 学时 前置：/advanced/10-security、/advanced/08-testing-local-chain验证于 2026-11-04

本章目标 ​

完成这一章后，你应该能够：

  • 按“范围 → 威胁模型 → 静态检查 → PoC → 修复 → 回归”的流程做一次小型审计。
  • 把漏洞写成可复现的测试，而不是只给一句结论。
  • 区分漏洞类别、严重级别与业务影响。
  • 知道正则规则、Slither、模糊测试与形式化验证各自能做什么。
  • 输出一份可执行的审计报告与修复清单。

前置检查 ​

  • 已完成 10 · 合约安全 与 08 · 测试与本地链。
  • 能读懂重入、访问控制、预言机操纵与精度问题。
  • 会写 Hardhat 测试与自定义错误断言。

本章示例位于 examples/18-audit，包含漏洞版、攻击合约、修复版与 16 条测试。

1. 审计不是“找 bug 清单” ​

一次可交付的审计至少包含：

  1. 范围：哪些合约、哪些函数、哪些外部依赖。
  2. 威胁模型：攻击者能做什么，不能做什么。
  3. 证据：每个问题都有复现步骤或明确的理论路径。
  4. 修复建议：具体到函数与状态顺序。
  5. 回归：修复后攻击失败、正常路径仍可用。

没有 PoC 的问题只能算“怀疑”，不能算“确认”。

2. 靶场：两个可复现漏洞 ​

solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

/// @title AuditVault
/// @notice 审计靶场：包含两个可复现漏洞，请勿用于生产。
/// @dev 漏洞 1：withdrawAll 先转账后清零，可被重入。
/// @dev 漏洞 2：setFeeRecipient 缺少访问控制。
// #region vulnerable-vault
contract AuditVault {
    mapping(address => uint256) public balances;
    address public feeRecipient;

    event Deposited(address indexed account, uint256 amount);
    event Withdrawn(address indexed account, uint256 amount);

    function deposit() external payable {
        balances[msg.sender] += msg.value;
        emit Deposited(msg.sender, msg.value);
    }

    function withdrawAll() external {
        uint256 amount = balances[msg.sender];

        // 先外部调用，后更新状态：重入窗口
        (bool ok, ) = msg.sender.call{ value: amount }('');
        require(ok, 'transfer failed');

        balances[msg.sender] = 0;
        emit Withdrawn(msg.sender, amount);
    }

    // 缺少 onlyOwner：任何人都能改收款地址
    function setFeeRecipient(address recipient) external {
        feeRecipient = recipient;
    }
}
// #endregion

4. 修复：CEI + 重入锁 + 访问控制 ​

solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

/// @title AuditVaultFixed
/// @notice 审计靶场的修复版：CEI + nonReentrant + 访问控制。
// #region fixed-vault
contract AuditVaultFixed {
    mapping(address => uint256) public balances;
    address public owner;
    address public feeRecipient;
    uint256 private locked;

    event Deposited(address indexed account, uint256 amount);
    event Withdrawn(address indexed account, uint256 amount);

    error NotOwner();
    error NoBalance();
    error ReentrantCall();
    error ZeroAddress();

    modifier onlyOwner() {
        if (msg.sender != owner) revert NotOwner();
        _;
    }

    modifier nonReentrant() {
        if (locked == 1) revert ReentrantCall();
        locked = 1;
        _;
        locked = 0;
    }

    constructor() {
        owner = msg.sender;
    }

    function deposit() external payable {
        balances[msg.sender] += msg.value;
        emit Deposited(msg.sender, msg.value);
    }

    function withdrawAll() external nonReentrant {
        uint256 amount = balances[msg.sender];
        if (amount == 0) revert NoBalance();

        // 先清零，再转账：即使被重入也读不到余额
        balances[msg.sender] = 0;
        (bool ok, ) = msg.sender.call{ value: amount }('');
        require(ok, 'transfer failed');

        emit Withdrawn(msg.sender, amount);
    }

    function setFeeRecipient(address recipient) external onlyOwner {
        if (recipient == address(0)) revert ZeroAddress();
        feeRecipient = recipient;
    }
}
// #endregion

三处关键改动：

  1. Checks-Effects-Interactions：先把 balances[msg.sender] 清零，再转账。
  2. nonReentrant：即使未来有人调整顺序，重入也会被锁挡住。
  3. onlyOwner + 零地址检查：把配置权限收回到 owner，并拒绝无效地址。

修复要成对验证

只测“攻击失败”不够，还要测“正常用户仍然能提款”。否则很容易修成“谁都不能用”。

5. 规则扫描：能做什么，不能做什么 ​

javascript
// #region audit-rules
const RULES = [
  {
    id: 'tx-origin',
    severity: 'high',
    pattern: /\btx\.origin\b/,
    message: 'tx.origin 用于授权，可能被钓鱼合约利用'
  },
  {
    id: 'selfdestruct',
    severity: 'high',
    pattern: /\bselfdestruct\s*\(/,
    message: 'selfdestruct 会改变合约存在性，需确认业务与升级方案'
  }
]

function hasGuard(source) {
  return /nonReentrant/.test(source)
}

function findMissingAccessControl(source) {
  const findings = []
  const functionPattern = /function\s+(set[A-Z]\w*)\s*\([^)]*\)\s*(external|public)([^{]*)\{/g

  for (const match of source.matchAll(functionPattern)) {
    const [, name, visibility, tail] = match
    if (!/onlyOwner|onlyRole|onlyAdmin|onlyGovernance/.test(tail)) {
      findings.push({
        id: 'missing-access-control',
        severity: 'medium',
        message: `${visibility} 函数 ${name} 未声明访问控制修饰器`
      })
    }
  }

  return findings
}

/**
 * 教学用正则审计：只做模式匹配，不能替代 Slither、人工审计与形式化验证。
 */
export function auditSource(source) {
  const findings = []

  for (const rule of RULES) {
    if (rule.pattern.test(source)) {
      findings.push({ id: rule.id, severity: rule.severity, message: rule.message })
    }
  }

  for (const line of source.split('\n')) {
    if (/\.call\s*\(/.test(line) && !/=\s*[^;]*\.call\s*\(/.test(line)) {
      findings.push({
        id: 'unchecked-call',
        severity: 'high',
        message: '低层 call 的返回值未赋给变量'
      })
    }
  }

  if (/\.call\s*\{[^}]*value\s*:/.test(source) && !hasGuard(source)) {
    findings.push({
      id: 'reentrancy-risk',
      severity: 'high',
      message: '外部 value 调用前未发现 nonReentrant 保护，检查是否遵循 CEI'
    })
  }

  findings.push(...findMissingAccessControl(source))
  return findings.sort((a, b) => a.id.localeCompare(b.id))
}
// #endregion

import { readFileSync } from 'node:fs'

console.log(`审计目标: ${target}`)
if (findings.length === 0) {
  console.log('未发现规则命中的问题（不代表合约安全）')

6. 形式化与不变量 ​

形式化验证的核心是把业务性质写成可检查的规格，例如：

  • 总供应量等于所有余额之和。
  • 任何用户不能提取超过自己的余额。
  • 清算后协议不会产生坏账。
  • 管理员不能直接拿走用户资金。

工具选择：

  • Slither：静态分析，适合快速发现常见模式。
  • Foundry invariant/fuzz：适合状态机与边界。
  • Certora / SMTChecker：适合关键不变量，但建模成本高。
  • 人工审计：负责业务语义、经济模型与组合风险。

本环境未安装 Slither/Foundry，示例只用 Hardhat 测试与正则规则；结论中必须注明工具边界。

7. 严重级别与报告模板 ​

级别判断标准
Critical直接盗取资金、永久冻结、协议破产
High条件性资金损失、权限提升、关键状态损坏
Medium有限损失、可恢复、需要特定条件
Low配置错误、边界不一致、信息泄露
Info可读性、事件、文档与最佳实践

报告至少包含：

8. 审计清单 ​

  • 外部调用是否遵循 CEI？
  • 所有状态修改函数是否有访问控制？
  • 低层 call 返回值是否检查？
  • 是否使用 tx.origin 授权？
  • 预言机是否可被单区块操纵？
  • 是否有精度损失、舍入方向错误？
  • 签名是否含 chainId、nonce 与过期时间？
  • 升级函数是否有 timelock / 多签？
  • 紧急暂停是否会冻结用户资金？
  • 事件是否覆盖关键状态变更？

9. 测试覆盖 ​

16 条测试：

  • 8 条靶场测试：重入 PoC、修复版回滚、正常提取、零余额、访问控制、零地址、存款事件。
  • 8 条规则测试：tx.origin、重入、nonReentrant 抑制、访问控制、onlyOwner 抑制、未检查 call、selfdestruct、干净片段。

10. 常见坑 ​

  • 只修复不回归：修复后没有重新跑攻击测试。
  • 只测攻击失败：修成“所有人都不能用”也算回归。
  • 把工具输出当结论：静态分析需要人工确认与 PoC。
  • 忽略业务语义：代码“符合模式”不代表经济模型安全。
  • 报告没有范围：没说明哪些依赖、哪些链、哪些版本。
  • 修复引入新中心化风险：onlyOwner 本身也需要多签与 timelock。

11. 练习题 ​
