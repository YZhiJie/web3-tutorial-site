练习 1：增加 gas 成本，计算攻击者净收益

攻击者的净利润等于毛利润减去 gas 成本折算成 A 的数量：

text
netProfitA = attackerProfitA - (gasUsed × gasPriceWei) / priceOfAInWei
1

在 src/mev.mjs 末尾追加一个纯函数：

js
/** gasUsed / gasPriceWei / priceOfAInWei 都从真实交易收据与池子报价取得 */
export function netProfitA(result, { gasUsed, gasPriceWei, priceOfAInWei }) {
  if (priceOfAInWei === 0n) throw new Error('priceOfAInWei must be positive')
  const gasCostWei = gasUsed * gasPriceWei
  const gasCostA = Number(gasCostWei) / Number(priceOfAInWei)
  return result.attackerProfitA - gasCostA
}

练习 2：模拟“受害者先成交、攻击者后置卖出”，比较两种排序

同一组参数下，受害者先成交会拿到诚实价格，攻击者只能以更差的储备比例卖出：

js
export function simulateBackrun(pool, { victimAmountIn, attackerAmountIn }) {
  const state = pool.clone()

  const victimOut = state.swapAForB(victimAmountIn)
  const attackerBought = state.swapAForB(attackerAmountIn)
  const attackerBackOut = state.swapBForA(attackerBought)

  return {
    victimOut,
    attackerBought,
    attackerBackOut,
    attackerProfitA: attackerBackOut - attackerAmountIn,
    finalReserveA: state.reserveA,
    finalReserveB: state.reserveB
  }
}

练习 3：实现 TWAP 滑点下限，观察大额交易失败率

用最近若干次报价的均值作为参考价，再乘容忍区间：

js
export function twap(prices) {
  if (prices.length === 0) throw new Error('price history is empty')
  return prices.reduce((sum, price) => sum + price, 0) / prices.length
}

export function twapMinAmountOut(history, toleranceBps = 100) {
  return twap(history) * (1 - toleranceBps / 10_000)
}

统计不同前置规模下受害者交易的回滚次数：

js
import {
  ConstantProductPool,
  SlippageExceeded,
  simulateHonest,
  swapWithSlippage,
  twapMinAmountOut
} from '../src/mev.mjs'

const pool = new ConstantProductPool(1000, 1000, 30)
const victimAmountIn = 100
const honestOut = simulateHonest(pool, { victimAmountIn })

// 教学用历史序列：真实系统应取过去 N 个区块的链上价格
const history = [honestOut * 1.01, honestOut, honestOut * 0.99]
const minOut = twapMinAmountOut(history, 100)

const sizes = [20, 40, 60, 80, 100, 120, 140, 160, 180, 200]
let failures = 0

for (const size of sizes) {
  const attacked = pool.clone()
  attacked.swapAForB(size)
  try {
    swapWithSlippage(attacked, victimAmountIn, minOut)
  } catch (error) {
    if (error instanceof SlippageExceeded) failures += 1
  }
}

console.log(`TWAP 下限: ${minOut.toFixed(4)} B`)
console.log(`失败率: ${failures}/${sizes.length}`)

（scripts/twap-check.mjs 是本练习新增文件。）观察重点：

  • TWAP 窗口越长，下限越平滑，但越容易滞后于真实价格。
  • 窗口越短，越容易被同一区块内的前置交易操纵。
  • 下限收紧会降低被夹概率，也会提高正常波动下的失败率；失败交易仍然消耗 gas。

不要把这个脚本当成生产风控；真实实现需要多源价格、时间加权、异常值剔除与链上监控。

练习 4：设计 commit-reveal 的清算流程与状态机

核心目标是让“提交清算意图”与“公开价格/参数”分离，减少公开 mempool 中的抢跑。

状态机：

状态进入条件可执行动作
None初始commit(hash)
Committed已提交 keccak256(abi.encode(user, price, salt, nonce))等待 commit 窗口结束；可 cancel
Revealed在 reveal 窗口内提交原像且哈希匹配等待执行延迟；可被争议/取消
Executed清算成功且状态已更新终态
Expired超过 reveal 截止时间仍未揭示退还保证金，重新开放

约束：

  • commit 内必须绑定 user、price、salt、nonce 和 chainId，防止跨地址/跨链重放。
  • reveal 只能在 commit 截止之后、reveal 截止之前进行。
  • 执行前先把状态置为 Executed，再外部调用，遵循 CEI。
  • 每个用户同一轮只能有一个有效 commit；新一轮用 nonce 区分。
  • 揭示期仍然会暴露价格，因此大额清算应使用批量拍卖或阈值解密，而不是逐笔 reveal。

最小伪代码：

solidity
enum Phase { None, Committed, Revealed, Executed }

mapping(address => bytes32) public commitments;
mapping(address => Phase) public phase;
uint256 public immutable commitEnd;
uint256 public immutable revealEnd;

function commit(bytes32 commitment) external {
    require(phase[msg.sender] == Phase.None, "already committed");
    commitments[msg.sender] = commitment;
    phase[msg.sender] = Phase.Committed;
}

function reveal(address user, uint256 price, bytes32 salt, uint256 nonce) external {
    require(block.timestamp >= commitEnd, "commit window open");
    require(block.timestamp <= revealEnd, "reveal expired");
    require(phase[msg.sender] == Phase.Committed, "not committed");
    require(
        keccak256(abi.encode(user, price, salt, nonce, block.chainid)) == commitments[msg.sender],
        "bad reveal"
    );
    phase[msg.sender] = Phase.Revealed;
    // 记录价格，等待执行延迟
}

练习 5：dApp MEV 风险清单（用户 / 协议 / 监控）
分类检查项目的
用户设置最小输出与 deadline，不使用无限滑点阻止单笔被夹与旧交易延迟执行
用户大额交易拆单或走 TWAP / RFQ降低公开 mempool 中的信号强度
用户优先使用聚合器或私有交易通道减少被抢跑与前置的概率
用户核对交易模拟结果与价格影响避免在异常池状态下成交
协议关键状态变更使用 commit-reveal隐藏意图，降低抢跑窗口
协议清算与拍卖使用批量或延迟执行避免逐笔排序套利
协议价格使用 TWAP 或多源预言机降低单区块价格操纵
协议参数变更走 timelock给用户与监控反应时间
协议对同一区块内的异常顺序做限制降低三明治与回滚组合
监控监控大额 swap、异常价格影响与失败率及早发现攻击与异常订单流
监控监控同一地址的连续前置/后置交易识别 searcher 行为
监控监控 L2 排序器与私有通道的健康度避免把“无 MEV”当成默认事实
监控建立告警值班与应急预案出事时能暂停、降级或切换通道

结论：滑点保护只保护“这一笔成交”，不能消除失败交易、gas 消耗与协议级排序风险；防护要同时覆盖用户参数、协议设计与监控。
