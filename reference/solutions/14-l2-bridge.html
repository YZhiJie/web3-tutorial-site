练习 1：给 Bridge 增加每日提款限额，并测试边界

在 Bridge 中增加按“L2 区块窗口”统计的限额：

} = {}) {
  this.l1Finality = l1Finality
  this.challengePeriod = challengePeriod
  this.dailyWithdrawalLimit = dailyWithdrawalLimit
  this.blocksPerDay = blocksPerDay

burn 改为：

js
burn({ from, amount, nonce, l2Block, l1Block }) {
  const value = BigInt(amount)
  if (value <= 0n) fail('ZeroAmount', 'burn amount must be positive')
  if (value > this.#l2Supply) fail('InsufficientSupply', 'burn exceeds L2 supply')

  const withdrawal = {
    kind: 'withdrawal',
    from,
    to: from,
    amount: value,
    nonce: String(nonce),
    l2Block: Number(l2Block),
    l1Block: Number(l1Block),
    availableAtL1Block: Number(l1Block) + this.challengePeriod
  }
  withdrawal.id = messageId(withdrawal)

  if (this.#pendingWithdrawals.has(withdrawal.id) || this.#processed.has(withdrawal.id)) {
    fail('DuplicateMessage', `message ${withdrawal.id} already exists`)
  }

  const day = Math.floor(Number(l2Block) / this.blocksPerDay)
  const used = this.#withdrawalsByDay.get(day) ?? 0n
  if (used + value > this.dailyWithdrawalLimit) {
    fail('DailyLimitExceeded', `daily limit ${this.dailyWithdrawalLimit} exceeded`)
  }

  this.#withdrawalsByDay.set(day, used + value)
  this.#pendingWithdrawals.set(withdrawal.id, value)
  this.#l2Supply -= value
  return withdrawal
}

边界测试：

js
test('每日提款限额：等于上限成功，超出 1 wei 失败，次日恢复', () => {
  const bridge = new Bridge({
    l1Finality: 3,
    challengePeriod: 5,
    dailyWithdrawalLimit: 10n ** 18n,
    blocksPerDay: 100
  })

  const deposit = bridge.deposit({
    from: '0xAlice',
    amount: 2n * 10n ** 18n,
    nonce: 'deposit-1',
    l1Block: 100
  })
  bridge.relayDeposit(deposit, { l1Head: 103 })

  const first = bridge.burn({
    from: '0xAlice',
    amount: 10n ** 18n,
    nonce: 'withdraw-1',
    l2Block: 0,
    l1Block: 200
  })
  assert.ok(first)

  assert.throws(
    () => bridge.burn({
      from: '0xAlice',
      amount: 1n,
      nonce: 'withdraw-2',
      l2Block: 0,
      l1Block: 200
    }),
    expectBridgeError('DailyLimitExceeded')
  )

  const nextDay = bridge.burn({
    from: '0xAlice',
    amount: 1n,
    nonce: 'withdraw-3',
    l2Block: 100,
    l1Block: 200
  })
  assert.ok(nextDay)
  assert.equal(bridge.invariantHolds(), true)
})

要点：

  • 限额检查放在重复消息检查之后、任何状态变更之前；失败时 l2Supply 和待领取集合都不变。
  • l2Block: 0 与 l2Block: 100 落在两个不同的 blocksPerDay 窗口，第二天自动重置。
  • 这是全局限额，不是单用户限额；生产桥通常同时有“单用户限额 + 全局限额 + 速率限制”。
  • 用区块窗口是教学简化。真实系统应使用时间戳桶，并考虑 L2 出块抖动。
  • 还需要防绕过：待领取的提款也应计入风险敞口，管理员应能暂停、调整限额，并对 DailyLimitExceeded 告警。
练习 2：把消息 ID 换成 keccak256，并比较与 sha256 的取舍

node:crypto 没有直接提供 Ethereum 的 keccak256，需要给 14 示例加一个依赖：

bash
pnpm --filter @web3-ex/14-l2-bridge add ethers
1

把 src/bridge.mjs 中的导入与 messageId 改成：

js
import { keccak256, toUtf8Bytes } from 'ethers'

export function messageId(payload) {
  return keccak256(toUtf8Bytes(canonical(payload)))
}

canonical 仍保持固定字段顺序。测试不需要改断言，因为所有 ID 都是运行时重新计算的。

取舍：

维度keccak256sha256
依赖需要 ethers 等库Node 内置，零依赖
链上验证EVM 原生 keccak256 操作码，便宜SHA-256 预编译，成本更高
生态一致性Ethereum 事实标准，便于和合约对齐通用标准，更适合纯链下系统
安全强度抗碰撞，足够做消息 ID抗碰撞，足够做消息 ID
迁移成本ID 会全部变化，需要重建索引/待处理队列保持现状

要点：

  • 消息 ID 不是签名，不需要“不可伪造”的密钥假设；它只需要稳定、抗碰撞、能唯一标识字段组合。
  • 如果桥合约要在链上重算并校验 ID，优先 keccak256，避免在 Solidity 里做字符串 JSON 解析。
  • 更稳妥的做法是直接用 ABI 编码固定字段，而不是 JSON 字符串；跨语言时 JSON 的空白、数字格式、字段顺序都可能变化。
  • 切换哈希会让旧 ID 全部失效。生产环境要版本化消息格式，旧消息继续用旧算法，或者停机迁移。
  • 无论用哪种哈希，都要把 chainId、桥合约地址、方向（deposit/withdrawal）纳入 ID，防止跨链或跨方向重放。
练习 3：设计“批次未可用”失败状态、重试与告警

真实桥的取款通常不是“挑战期一到就能领”，还要等 L1 上的批次/根被发布。建议状态机：

text
PENDING
  ├─ BATCH_NOT_AVAILABLE  （可重试，批次还没上 L1）
  ├─ NOT_FINAL            （可重试，确认数/挑战期未到）
  ├─ CLAIMABLE            （可领取）
  └─ EXPIRED              （需要人工复核）

重试封装：

js
import { BridgeError } from './bridge.mjs'

async function claimWithRetry(bridge, withdrawal, {
  l1Head,
  maxAttempts = 5,
  baseDelayMs = 1000
} = {}) {
  for (let attempt = 0; attempt < maxAttempts; attempt += 1) {
    try {
      return bridge.claimWithdrawal(withdrawal, { l1Head })
    } catch (error) {
      if (!(error instanceof BridgeError)) throw error
      if (error.code !== 'NotFinal' && error.code !== 'BatchNotAvailable') {
        throw error
      }
      if (attempt === maxAttempts - 1) break
      await new Promise((resolve) =>
        setTimeout(resolve, baseDelayMs * 2 ** attempt)
      )
    }
  }

  throw new BridgeError(
    'RetryExhausted',
    `withdrawal ${withdrawal.id} is still not claimable`
  )
}

要点：

  • NotFinal 与 BatchNotAvailable 是可重试错误；InvalidMessage、ReplayDetected、WrongDirection 是终止错误，重试没有意义。
  • 重试不要改变 withdrawal.id 或金额；只改变 l1Head 与等待时间。
  • 超过最大次数后进入 RetryExhausted，写告警、保留待领取记录，不要标记为已处理。
  • 重试要有上限、抖动和退避，避免所有客户端同时打爆 RPC。
  • 运维面板应展示每种状态的队列长度、最老一笔的等待时长、最近错误码。
  • 当前教学模型只有 NotFinal；接入真实桥时，在批次查询失败的分支抛出 BatchNotAvailable，其余逻辑不变。
练习 4：模拟“存款后 L1 重组”，验证不会重复铸币

给 Bridge 增加一个“L1 重组回滚存款”的方法：

js
revertDeposit(message) {
  assertMessage(message, 'deposit')

  if (this.#processed.has(message.id)) {
    fail('AlreadyProcessed', 'cannot revert a deposit that was already relayed')
  }

  const pending = this.#pendingDeposits.get(message.id)
  if (pending === undefined) {
    fail('UnknownMessage', `deposit ${message.id} is not pending`)
  }

  this.#pendingDeposits.delete(message.id)
  this.#l1Locked -= pending
}

测试：

js
test('存款后 L1 重组，最终性后也不会重复铸币', () => {
  const bridge = new Bridge({ l1Finality: 12 })
  const deposit = makeDeposit(bridge)

  // 重组前还没达到最终性，中继被拒绝，没有铸币
  assert.throws(
    () => bridge.relayDeposit(deposit, { l1Head: 105 }),
    expectBridgeError('NotFinal')
  )
  assert.equal(bridge.l2Supply, 0n)

  // L1 重组把该存款交易回滚，桥同步删除待中继记录
  bridge.revertDeposit(deposit)

  // 即使之后 L1 达到最终性，也找不到这条存款
  assert.throws(
    () => bridge.relayDeposit(deposit, { l1Head: 120 }),
    expectBridgeError('UnknownMessage')
  )

  assert.equal(bridge.l2Supply, 0n)
  assert.equal(bridge.l1Locked, 0n)
  assert.equal(bridge.pendingDepositAmount, 0n)
  assert.equal(bridge.invariantHolds(), true)
})

要点：

  • 关键防护是“L1 达到最终性之前不铸币”。如果重组发生在最终性之前，L2 还没有 mint，回滚是安全的。
  • revertDeposit 必须同时删除待中继记录并减少 l1Locked，否则守恒式会被破坏。
  • 如果存款已经中继（#processed 已包含），不能简单回滚；那说明最终性假设被打破，需要暂停桥、治理介入或保险赔付。
  • 真实系统还要处理“取款领取后 L1 重组”的反向情况：记录领取所在区块，重组时回滚 processed 标记，避免用户既拿到 L1 资产又保留 L2 权利。
  • 重组深度超过最终性窗口时，任何桥都无法仅靠代码保证安全，必须有运维与治理预案。
练习 5：Optimistic 与 ZK 提现等待时间对比
维度Optimistic RollupZK Rollup
提现原理批次上 L1，等待挑战期批次 + 有效性证明上 L1
官方桥等待挑战期，常见几分钟到数天证明生成 + L1 验证，常见几分钟到数小时
最终性来源挑战期结束且无人成功挑战证明通过 L1 验证
主要风险欺诈证明可用性、挑战期长、排序器审查电路/证明系统漏洞、验证成本、证明生成延迟
成本无需生成证明，成本较低证明生成成本较高，但可摊薄
用户体验官方桥慢，常依赖第三方 fast bridge官方桥相对快，但证明未出时仍需等
L1 → L2等 L1 最终性后入账同左，通常还要等批次

要点：

  • 两种桥的“等待”都不是纯粹的密码学时间，还包含批次发布、L1 确认、排序器/证明者可用性。
  • Optimistic 的挑战期是为了给欺诈证明留时间；挑战期越长越安全，但提现越慢。
  • ZK 的等待主要取决于证明生成与验证；证明确认后，通常不需要再等挑战期。
  • 第三方 fast bridge 用流动性提供者先垫付，用户快，但引入了对流动性方的信任与对手方风险。
  • 选择方案时要同时看安全假设、资本效率、用户体验和运维复杂度，不能只看“多少分钟到账”。
