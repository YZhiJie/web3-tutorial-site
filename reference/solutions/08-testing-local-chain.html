练习 1：增加 extendDeadline，只允许仲裁人延长，并补边界测试

deadline 原来是 immutable，无法修改，先改成普通状态变量：

solidity
uint256 public deadline;
1

增加事件与错误：

solidity
event DeadlineExtended(uint256 previousDeadline, uint256 newDeadline);
error DeadlineNotExtended(uint256 currentDeadline, uint256 newDeadline);
1
2

增加函数：

solidity
function extendDeadline(uint256 newDeadline) external onlyArbiter {
    if (state == State.RELEASED || state == State.REFUNDED) revert InvalidState(state);
    if (newDeadline <= deadline) revert DeadlineNotExtended(deadline, newDeadline);

    emit DeadlineExtended(deadline, newDeadline);
    deadline = newDeadline;
}

两条边界测试：

ts
it('只有仲裁人可以延长，且不能缩短或保持不变', async () => {
  const { escrow, buyer, arbiter, deadline } = await fundEscrow()

  await expect(escrow.connect(buyer).extendDeadline(deadline + DAY))
    .to.be.revertedWithCustomError(escrow, 'NotArbiter')
    .withArgs(buyer.address)

  await expect(escrow.connect(arbiter).extendDeadline(deadline))
    .to.be.revertedWithCustomError(escrow, 'DeadlineNotExtended')
    .withArgs(BigInt(deadline), BigInt(deadline))

  await expect(escrow.connect(arbiter).extendDeadline(deadline - 1))
    .to.be.revertedWithCustomError(escrow, 'DeadlineNotExtended')
    .withArgs(BigInt(deadline), BigInt(deadline - 1))
})

it('延长后按新截止时间放行，旧截止时间不再放行', async () => {
  const { escrow, buyer, arbiter, deadline } = await fundEscrow()
  const nextDeadline = deadline + DAY

  await escrow.connect(arbiter).extendDeadline(nextDeadline)

  await time.increaseTo(deadline)
  await expect(escrow.connect(buyer).claimAfterDeadline())
    .to.be.revertedWithCustomError(escrow, 'DeadlineNotReached')

  await time.increaseTo(nextDeadline)
  await expect(escrow.connect(buyer).claimAfterDeadline())
    .to.emit(escrow, 'Refunded')
})

要点：

  • “只能延长”要用 <= 判断，等于旧值也必须拒绝，否则会产生无意义的事件。
  • extendDeadline 只允许 AWAITING 与 FUNDED，已经结算的托管不能再改截止时间。
  • 事件先发、再写状态，读事件时看到的 previousDeadline 才是旧值。
  • 延长会直接改变买家的自救时间，生产项目应只允许仲裁人在特定条件下调用，并对事件做监控。
练习 2：用固定种子生成 100 个随机金额，保证失败可复现

在测试文件顶部增加一个确定性伪随机函数：

ts
function seededRandom(seed: number) {
  let state = seed >>> 0
  return () => {
    state = (state * 1664525 + 1013904223) >>> 0
    return state / 2 ** 32
  }
}

it('固定种子的 100 个随机金额下不变量始终成立', async () => {
  const random = seededRandom(20261104)

  for (let i = 0; i < 100; i += 1) {
    const { escrow, buyer, arbiter } = await loadFixture(deployEscrowFixture)
    const value = BigInt(1 + Math.floor(random() * 1000)) * 10n ** 15n

    await escrow.connect(buyer).fund({ value })
    expect(await escrow.invariantHolds(), `fund #${i}`).to.equal(true)

    if (i % 2 === 0) {
      await escrow.connect(buyer).release()
    } else {

    expect(await escrow.invariantHolds(), `settle #${i}`).to.equal(true)
    expect(await ethers.provider.getBalance(await escrow.getAddress())).to.equal(0n)
  }

练习 3：RELEASED 后再次调用 release，断言当前状态

先注意修饰器顺序。release() 的声明是：

solidity
function release() external onlyParticipant inState(State.FUNDED)
1

卖家不是 buyer 也不是 arbiter，所以卖家调用会先命中 onlyParticipant，得到 NotBuyerOrArbiter，不会走到状态检查。直接断言 InvalidState 会失败。

如果题目要求“卖家调用”，正确的断言是：

ts
it('卖家无权调用 release，错误里带调用者地址', async () => {
  const { escrow, buyer, seller } = await fundEscrow()
  await escrow.connect(buyer).release()

  await expect(escrow.connect(seller).release())
    .to.be.revertedWithCustomError(escrow, 'NotBuyerOrArbiter')
    .withArgs(seller.address)
})

  expect(await escrow.state()).to.equal(2n) // RELEASED

要点：

  • 修饰器从左到右执行，权限检查在状态检查之前。
  • 不要为了“让测试通过”把 inState 挪到 onlyParticipant 前面；那会把内部状态泄露给无关账户，也会改变错误语义。
  • 断言自定义错误的参数，比只断言 reverted 更能定位状态机问题。
练习 4：设计“余额不超过所有托管金额之和”的不变量

在 Escrow 中增加两个只读函数：

solidity
function totalEscrowed() public view returns (uint256) {
    return state == State.FUNDED ? amount : 0;
}

function balanceNeverExceedsEscrow() external view returns (bool) {
    return address(this).balance <= totalEscrowed();
}

it('任何合法路径下，合约余额都不超过托管总额', async () => {
  const { escrow, buyer } = await fundEscrow()
  expect(await escrow.balanceNeverExceedsEscrow()).to.equal(true)

  await escrow.connect(buyer).release()
  expect(await escrow.balanceNeverExceedsEscrow()).to.equal(true)

  await expect(escrow.connect(buyer).claimAfterDeadline())
    .to.be.revertedWithCustomError(escrow, 'InvalidState')
})

为什么在当前单合约模型下它和 invariantHolds 等价：

  • 当前只有一个托管，totalEscrowed() 只可能是 amount（FUNDED）或 0（其他状态），所以上界就是 invariantHolds 里的等式右端。
  • 合法路径中，fund 是唯一的 ETH 入口，release / refund / claimAfterDeadline 都会先改状态再转账。因此不会出现“状态仍是 FUNDED、余额却低于 amount”的可达状态；小于号在合法路径上不会发生。
  • 如果有人用 selfdestruct 或区块奖励强制转入 ETH，余额会大于托管总额，两个检查都会返回 false。这正是我们想要的告警。
  • 如果扩展成“同一个合约管理多笔托管”，就必须维护所有托管金额之和，并给每笔托管独立记账；只看 address(this).balance 已经无法区分哪一笔属于谁。
