练习 1：给 AccessVault 增加 ERC-20 救援函数

在 AccessVault.sol 顶部增加最小接口：

solidity
interface IERC20 {
    function transfer(address to, uint256 amount) external returns (bool);
}

2
3

在权限区域增加：

solidity
error InvalidToken();

function rescue(address token, uint256 amount) external onlyOwner {
    if (token == address(0) || token.code.length == 0) revert InvalidToken();

    (bool ok, bytes memory data) =
        token.call(abi.encodeCall(IERC20.transfer, (owner, amount)));
    if (!ok) revert TransferFailed();
    if (data.length > 0 && (data.length < 32 || !abi.decode(data, (bool)))) {
        revert TransferFailed();
    }
}

要点：

  • 只允许 owner 调用，并且代币只能转给 owner，不能转给任意地址。
  • 兼容两种常见 ERC-20：返回 true 的标准代币，以及不返回值的旧代币；返回 false 时视为失败。
  • 不加 ETH 版本，是因为合约里的 ETH 全部对应 pendingWithdrawals 的用户负债。owner 若能提取 ETH，就等于拥有随时挪用用户资金的后门，和“用户自己提款是唯一出口”的设计冲突。
  • 如果确实需要清理误转入的 ETH，必须单独计算“未被记账的盈余”，例如 address(this).balance - totalPendingWithdrawals，并且只提取这部分；本示例没有维护总负债，所以不提供 ETH 救援。
  • 生产环境应把 owner 换成多签 + timelock，并对 rescue 发事件、设延迟。以上仍是教学实现。
练习 2：支持批量提现，单笔失败不影响其他账户

增加一个失败事件，便于链下监控：

solidity
event WithdrawalFailed(address indexed account, uint256 amount);
1

保留原来的单笔 withdraw，新增 withdrawBatch；如果题目要求 withdraw 本身接收数组，把函数签名改成数组参数即可，循环逻辑不变。

在 pull payment 区域增加批量函数：

solidity
function withdrawBatch(address[] calldata accounts) external nonReentrant {
    for (uint256 i = 0; i < accounts.length; i++) {
        address account = accounts[i];
        uint256 amount = pendingWithdrawals[account];
        if (amount == 0) continue;

        // 先清零，再转账：即使对方重入，读到的也是 0
        pendingWithdrawals[account] = 0;

        (bool ok, ) = account.call{value: amount}('');
        if (ok) {
            emit Withdrawal(account, amount);
        } else {
            // 失败时恢复记账，资金仍属于该账户，可稍后单独重试
            pendingWithdrawals[account] = amount;
            emit WithdrawalFailed(account, amount);
        }
    }
}

要点：

  • 这里不能用 require(ok)，否则一个收款方 revert 会让整批交易回滚，回到 push payment 的老问题。
  • 失败时把 pendingWithdrawals 恢复，保证资金不会因为一次失败调用而丢失。
  • nonReentrant 保护批量入口；生产中 withdraw 也应加同一个锁，并让两者共享内部提现函数。
  • 数组没有长度上限，调用方可能因为区块 gas 上限而失败。前端应按页传入，例如每批 50 个账户。
  • 如果收款方是恶意合约，可以消耗掉转发给它的 gas。需要更强隔离时，可给外部调用设置固定 gas 上限，但会牺牲对复杂合约的兼容性。
  • 恶意账户最多只能让自己的那一笔失败，无法影响其他账户的记账与提现。
练习 3：给 SimpleProxy 增加 upgradeToAndCall

在 SimpleProxy 中增加：

solidity
function upgradeToAndCall(address newImplementation, bytes calldata data) external payable {
    if (msg.sender != deployer) revert NotDeployer(msg.sender);
    if (newImplementation == address(0)) revert ZeroAddress();

    _setImplementation(newImplementation);

    (bool ok, bytes memory returndata) = newImplementation.delegatecall(data);
    if (!ok) {
        assembly {
            revert(add(returndata, 0x20), mload(returndata))
        }
    }
}

要点：

  • 升级和初始化在同一个交易里完成，不会出现“实现已经换了、但还没初始化”的中间状态。
  • 如果 delegatecall 失败，Solidity 会执行 revert，EVM 会把同一交易里的 sstore 一起回滚，因此实现地址仍然是旧的。这就是原子性，不需要手写“回滚实现地址”。
  • 如果初始化函数本身有 AlreadyInitialized 检查，重复调用会让整个升级交易失败，而不是悄悄跳过。
  • 初始化数据必须用新实现的 ABI 编码；升级前要检查存储布局，V2 只能在 V1 的变量之后追加。
  • 示例仍只允许 deployer 升级；生产环境应改为多签 + timelock，并给 upgradeToAndCall 加事件。
练习 4：测试升级到 V2 且 step 为 0 时 increment 仍为 +1

追加到 describe('SimpleProxy 升级')：

ts
it('升级到 V2 且 step 为 0 时，increment 仍为 +1', async () => {
  const { proxy, proxyAsV1 } = await deployProxy()
  const v2 = await ethers.deployContract('CounterV2')

  await proxyAsV1.initialize(10n)
  await proxy.upgrade(await v2.getAddress())

  const proxyAsV2 = await ethers.getContractAt('CounterV2', await proxy.getAddress())

  // step 是新增变量，升级后应默认为 0
  expect(await proxyAsV2.step()).to.equal(0n)
  expect(await proxyAsV2.value()).to.equal(10n)

  await proxyAsV2.increment()
  expect(await proxyAsV2.value()).to.equal(11n)
})
